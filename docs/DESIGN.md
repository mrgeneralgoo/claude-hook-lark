# 设计说明

这份文档记录 claude-hook-lark 的设计取舍。大部分结论来自对抗式代码审查中被实际复现出来的问题，
每一条都有对应的回归用例。日常使用不需要读这里，只在你想改代码、或想知道「为什么不那样做」时有用。

贯穿全文的一条原则：**隐私与过滤开关取最严解释，传输参数退回安全默认，凭据类型非法直接停发。**

---

## 一、为什么用 Webhook 而不是应用凭证

自定义机器人 webhook 不需要企业管理员审批、不需要维护 tenant token 缓存，一条 URL 即可用，
最符合「零依赖、开箱即用」。

如果你需要私聊推送（`app_id` / `app_secret` + `open_id`），在 `post()` 里换一个发送实现即可，
卡片构建逻辑可以完全复用。

## 二、卡片全部用 `json.dumps` 构建

用 shell 字符串拼 JSON 的做法，遇到引号、反斜杠、换行就会产出非法 JSON。
这里所有内容都经过 `json.dumps`，任务描述里出现什么字符都不会坏掉（有测试覆盖）。

---

## 二又二分之一、卡片用 schema 2.0

飞书卡片有两套 schema。v1 的正文是 `div` + `lark_md`，而 **lark_md 只支持粗体、行内代码、
链接这一小撮语法** —— Claude 的回复里常见的标题（`##`）、列表、代码块、引用统统会以原文形式
露在卡片上。2.0 的 `markdown` 元素支持完整得多，所以正文用它。

2.0 的几个坑，都是对着真实 API 一条条试出来的（`code 11246` = 卡片内容非法）：

| 元素 | 2.0 里是否可用 |
|------|---------------|
| `markdown` | ✅ 正文用它 |
| `hr` | ✅ |
| `div`（含 `fields` 两列写法） | ✅ 底部元信息仍用它 |
| `column_set` | ✅ |
| `note` | ❌ **一律被拒**，`elements` 里放 `plain_text` / `markdown` / `text` 都不行，换成 `text` 字段也不行 |

所以脚注改用一个 `markdown` 元素加灰色字体代替 `note`。另外元素挂在 `body.elements` 下，
不再是顶层 `elements`。

底部元信息（项目 / 分支 / 主机 / 会话 ID）全部走半宽字段排成两列 —— 让任何一项独占整行都是浪费。

## 三、配置的信任边界

`.claude/lark.json` 会随 `git clone` 一起进入你的机器。如果它能指定「发到哪」，
那么克隆任何一个第三方仓库，都可能让全局启用的插件把你的提问、Claude 的回复、
主机名和会话信息自动发往仓库作者控制的地址。

因此划了一条硬边界：

| 配置项 | 用户配置 / 环境变量 | 项目内 `.claude/lark.json` |
|--------|:---:|:---:|
| `webhook_url`、`secret` | ✅ | ❌ 忽略并告警 |
| `webhooks`、`allowed_hosts` | ✅ | ❌ 忽略并告警 |
| `webhook`（按名字引用） | ✅ | ✅ 名字必须已在用户配置中登记 |
| `debug` | ✅ | ❌ 忽略（否则仓库能让会话内容开始落盘） |
| `events`、`quiet_hours`、`include_summary`、`min_duration_seconds`、`timeout` | ✅ | ⚠️ 只能收窄 |

### 单调合并

项目配置对行为类字段只能更严、不能更松：

| 字段 | 合并方式 | 仓库能做什么 |
|------|----------|--------------|
| `events` | 取交集 | 只能减少事件，不能新增 |
| `include_summary` | 只允许 `true → false` | 只能关掉摘要，不能重新打开 |
| `min_duration_seconds` | 取较大值 | 只能过滤得更狠 |
| `timeout` | 取较小值 | 只能更快放弃 |
| `quiet_hours` | 用户未设时可新增 | 不能取消或改写用户设的静默时段 |

交集为空（例如用户只允许 `Notification`、项目只声明 `Stop`）的结果是**什么都不发**。

否则「项目只能收窄」就只是一句口号：仓库可以把你关掉的 `include_summary` 重新打开、
把 `quiet_hours` 抹掉、把 `debug` 开起来，让你明确禁用过的会话内容重新开始外发。

各层还必须**先各自校验、再合并**。直接拿原始值合并的话：
用户 `quiet_hours: []`（非法）+ 项目 `[22,8]` 会合并出一个合法值，用户本该触发的「全天静默」被洗掉；
用户 `timeout: 2` + 项目 `timeout: -1` 会先并成 `-1`、再被校验器改回 `5`，仓库反而把上限放宽了。

### 显式配置完全接管目的地

`CLAUDE_HOOK_LARK_CONFIG` 一旦生效，`webhook_url`、`secret`、具名表以及具名选择器 `webhook`
都不从用户级继承。否则一个 `{}` 或漏写 `webhook_url` 的配置仍是合法 JSON，会静默沿用上一级的群；
而只清地址、留下选择器的话，用户级选中的名字会去命中显式配置里的同名项，一样发到没被选中的群。

它指向的文件读不成（不存在、坏 JSON、无权限）时**停止发送** ——
你既然显式指定了它，就不该在它失效时悄悄退回上一级的群。

### 目的地校验

- 必须是 `https`，且主机需在 `allowed_hosts` 内（默认只允许飞书 / Lark 官方域名）。
- 主机取自 `urlsplit().hostname`，所以 `https://open.feishu.cn@attacker.com/…` 这类
  userinfo 伪装会被正确判为 `attacker.com` 并拒绝。
- **没有「不限制」这一档**：空数组会退回官方白名单，成员校验无条件执行。
- 项目配置**不跟随符号链接**（`O_NOFOLLOW`，并检查父目录），必须是普通文件、不超过 256 KiB，
  且用 `O_NONBLOCK` 打开。否则仓库提交一个 `.claude/lark.json -> /dev/zero` 或一个 FIFO，
  就能让每次 hook 无限阻塞。

## 四、配置项的类型校验

JSON 里的 `"false"`、`0`、`[]`、`"60"` 在 Python 真值语境下的行为都很反直觉 ——
`"false"` 是**真**值，`[]` 和 `0` 是**假**值。散在各个使用点做 `if cfg.get(x)` 判断必然漏，
所以类型校验集中在加载阶段一次做完，非法值按下表处理并写入告警（`doctor` 会打印）：

| 配置项 | 类型非法时 | 为什么这样选 |
|--------|-----------|-------------|
| `webhook_url`、`secret` | **停止发送** | 凭据类型不对就没法签名 / 发送 |
| `webhook`（具名选择器） | **停止发送** | `[]`/`0`/`false` 都是假值，会被当成「没配」而静默发往默认群 |
| `include_summary` | 按 `false` | 写成 `"false"` 是真值，你以为关了摘要其实没关 |
| `debug` | 按 `false` | 同上，不能让会话内容意外落盘 |
| `events` | 一个都不发 | 笔误不该反而放宽 |
| `quiet_hours` | **一直静默** | 你明确要求了静默时段，我们没法照办，宁可不发 |
| `min_duration_seconds` | 一直不满足（不发） | 过滤器失效不该变成「全放行」 |
| `timeout` | 退回默认 5 秒 | 传输参数，不该因为一个笔误就再也收不到通知 |
| `allowed_hosts` | 退回官方域名 | 字符串会被逐字符迭代；空数组若当成「不限制」等于关掉校验 |

几个要点：

- **NaN 尤其危险**：`耗时 < NaN` 恒为假，`min_duration_seconds: NaN` 会让门槛看似启用、实则永远放行。
  所以数值必须 `math.isfinite`。配置文件里的 `NaN` / `Infinity` **字面量**也会被拒绝 ——
  Python 的 `json` 默认接受它们，标准 JSON 并不允许。
- **凭据校验放在所有层级合并之后**（包括命令行 `--webhook`）。早校验会留下撤销不掉的 `_fatal`，
  导致「用户级地址类型写错 + 环境变量给了正确地址」这种本该正常发送的情况被跳过。
- `quiet_hours: null` 和 `min_duration_seconds: null` 是合法的「不启用」，不算非法值。

## 五、hook 不能拖慢或卡住会话

`plugin.json` 的硬超时是 15 秒。硬超时一旦触发进程会被**直接杀掉**，`except` 和 `exit 0` 都来不及执行，
用户会看到 hook timeout。所以内部必须明显更早收场。

- **9 秒单调时钟总预算**（`HOOK_BUDGET_SECONDS`）：Git 探测、transcript 解析、网络发送依次扣时间，
  网络超时取 `min(配置值, 剩余预算)`。有测试断言 `HOOK_BUDGET_SECONDS < plugin.json 的 timeout`。
- 光有预算不够 —— 它只能约束「我们主动传超时的调用」，管不到 `stdin.read()` 等 EOF、JSON 解析、
  文件读取这些内部阻塞。所以另外装了一个 **SIGALRM 墙钟看门狗**，9 秒后无差别打断当前操作。
- `HookTimeout` 刻意继承 `BaseException` 而非 `Exception`：本文件里到处是 `except Exception` 的兜底
  （读 stdin、写日志、跑 git），继承 `Exception` 会让看门狗在 stdin 处就被吞掉，
  然后带着空 payload 走完流程、把一张内容错误的卡片发出去。有测试断言超时后 `post` 调用次数为 **0**。
- 输入限量：stdin 1 MiB，transcript 超 16 MiB 只读尾部，HTTP 响应体只读 64 KiB。
- **畸形输入什么都不发**：空输入、解析失败、顶层不是对象、超过 1 MiB 被截断，一律直接退出。
  以前这些都被替换成 `{}` 再默认成 `Stop`，于是一段 `{broken` 就能伪造出一张「任务完成」卡片。
  截断判定靠多读一个字节 —— 被截断的 payload 解析出来可能仍然合法，但内容已经不完整。
- 其余一切异常都被吞掉并以 0 退出。

实测：父进程写入事件却不关闭管道时，hook 在 9.1 秒自行退出（退出码 0）；
38 MB 的 transcript 解析 0.185 秒；完整 hook 端到端 0.19 秒（本地）/ 0.56 秒（含真实网络）。

## 六、错误信息里永远不出现 webhook URL

URL 里的 token 等同密码，一次拼写错误就可能把它写进日志。

- 校验失败只报主机名，网络异常只报错误类别，顶层异常只记类型和出错位置。
- 日志目录 `0700`、文件 `0600`。
- **远端返回的文本一概不记**。代理的错误页会把请求路径原样打回来。这里没有采用「脱敏后再记录」：
  脱敏是模式匹配，挡不住任意编码变体（实测把连字符也百分号编码就能绕过）。
  所以 HTTP 错误只留状态码，业务错误只留数字 `code`，再配一份自己维护的静态说明
  （只收录亲自验证过含义的错误码，其余不猜）。
- 远端 `code` 必须先规范化成有限范围内的整数再使用 —— 否则把 `code` 塞成 URL 字符串就能绕过上面这条。
  同时注意 `False == 0`、`0.0 == 0`，直接写 `raw in (0, None)` 会把畸形响应当成发送成功。

## 七、什么才算「本轮任务」

Claude Code 的 transcript 里有一大堆 `type: "user"` 但不是人写的记录：

- 工具结果：顶层 `toolUseResult`，或 content 里的 `tool_result` block
- skill / slash command 展开出来的提示词：`isMeta`
- subagent 对话：`isSidechain`
- 上下文压缩摘要：`isCompactSummary`、`isVisibleInTranscriptOnly`
- 系统注入与命令输出：`<task-notification>`、`<local-command-stdout>`、各种 hook 输出

漏掉任何一类，卡片上「本轮任务」就会显示成系统文本，工具计数和耗时也会被错误重置。

麻烦在于**后面几类没有可信的结构化字段**能证明它来自系统 —— 你完全可以自己粘一段
`<task-notification>…` 让 Claude 分析。斜杠命令同理：`/model` 是纯控制，
`/review` 却会真正驱动一轮工作，光看记录区分不出来。

所以规则是：**凡是以保留标签开头的内容一律当作轮次边界，且不展示标签文本本身**；
纯图片 / 附件消息也是新一轮。

边界是**完整**的：任务、回答、工具计数、起始时间一起断开。只清任务不够 ——
上一轮的回答里往往复述了任务内容，留着它等于换个地方泄漏；不重置起始时间还会让耗时横跨两轮，
并让 3 秒的活绕过 60 秒门槛。

代价是：会话里出现过后台任务通知之后，卡片上「本轮任务」会变成
_（由命令或系统事件触发，内容不展示）_，工具统计也从边界重新算起。
这是刻意选的方向 —— 显示不全只是观感，而带出上一轮内容是泄漏。

### subagent 作用域

`isSidechain` 记录在更新任何统计**之前**就被排除掉，否则一条晚到的 subagent 记录会覆盖父轮的回答、
把它的工具计入父轮，还会把 2 秒的父轮拉长成一小时，从而绕过 `min_duration_seconds`。

`SubagentStop` 则相反：读 hook 事件里的 `agent_transcript_path`（子任务自己的 transcript，
记录都带 `isSidechain`）。事件里没带这个路径时**只发元数据卡片、不出摘要** ——
父文件里多个并发 subagent 的记录是交错的，「A 提问、B 提问、A 回答」会被拼成
「B 的任务 + A 的回答」，既是错误归因，也可能把另一个子任务的内容带出去。

### 损坏的 transcript 行

一条无法解析的行有可能正是轮次边界，跳过它就等于把上一轮的内容带进本轮。
但 Stop 触发时 Claude Code 往往正在追加写，文件最后一行经常是半截的 ——
要是连它也 fail closed，卡片就会长期空白。

判据有两条：

1. **这一行有没有以换行符结尾**。以换行结尾却解析失败 = 已经写完的坏记录，不是「还没写完」。
   这要求在 `strip()` **之前**记住换行信息，否则两种情况长得一模一样。
2. **后面是否还有正常记录**。

只有「单独一条、不以换行结尾、位于文件末尾」的坏行才容忍。连续两条坏行也不容忍 ——
追加写被打断只会留下一条半截尾行。

## 八、耗时未知时怎么办

设了 `min_duration_seconds` 却拿不到耗时（时间戳缺失、transcript 损坏、子任务作用域不可靠）就跳过推送 ——
放行等于让门槛在异常情况下自动失效。

但有一个例外：transcript 超过尾部上限时只解析尾部，一个工具密集的长任务可能整轮都比上限还大，
起始记录落在截断点之前。这时用尾部本身的时间跨度作为**可证明的下界**，只要下界已经超过门槛就照常推送 ——
否则会系统性漏掉最该提醒的那类长任务。

下界的起点在**每一道轮次边界都会重新播种**，否则新一轮的用户记录若缺时间戳，
下界就会横跨上一轮，让一个 3 秒的活混过 1 小时的门槛。

## 九、transcript 解析是尽力而为

文件不存在、某行是坏 JSON、编码异常，一律降级成「不带摘要的卡片」，绝不影响推送本身。
